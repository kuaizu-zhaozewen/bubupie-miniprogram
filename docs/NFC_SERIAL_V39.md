# 固定编号与碰一碰 V3.9

2026-11-26。编号属于每只实体IP，不属于IP款式、购买账号或手机。No.0001只是显示格式；0001与001在旧口头方案中是同一数值，程序统一至少四位，不截断10000及更大的编号。本轮预览仍用湾月现有素材，不代表新外观或命名已定稿。

## 现在怎样演示

“我的 → 碰一碰测试”进入公开一句话卡，显示No.0001；可切换No.0002、访客／已领养、低落／开心。切换身份不授予真实权益。首页原有testTap方法仍在，之前重排后按钮没挂出来，现在入口固定收在“我的”的开发演示区。mode非mock或enableDemoTools关闭时隐藏入口并拒绝演示领养。

开发者工具自定义编译：pages/card/index，参数id=star&demo=1&tag=DEMO-TAG-0001；第二只改DEMO-TAG-0002。领养预览：pages/bind/index?tag=DEMO-TAG-0001，输入BUBU-DEMO-BODY-001，确认弹窗显示固定编号；002配002，错配拒绝。回到公开卡仍显示同一编号，已领养可进详情。私码不进入公开分享参数，真实微信登录、扫码核销、读写芯片和服务端均未接入。

网页预览也可从“我的”进入；页面仅模拟碰到某只标签后的结果，不模拟无线信号。体验版正式触碰需要已开通能力、实物NDEF标签及机型联调，开发者工具按钮不代表已完成NFC。

## 首选路线 出厂配对 不要求消费者写卡

供应链先建立实体实例：instanceId（内部随机ID）、serialNo（全局唯一不可变显示号）、typeId（款式）、tagPublicToken（不可预测的公开查找令牌）、claimSecretHash（私密激活码摘要）、tagSn、batchId与质检状态。NFC硬件UID可留作质检辅助，不等于业务编号，不作为唯一防伪或领养依据。编号建议全品牌全局递增，需产品最终确认；不按款式重号，不因退款、解绑、换账号重排。

每只NFC出厂写入能带独立公开令牌的小程序NFC Scheme；包装内独立激活二维码指向同一instanceId，但携带私密核销凭证。外卡可印No.0001用于核对，不能把可猜编号当秘密。公开NFC与激活二维码不是同一个内容：公开入口任何人可看，私码只允许合法持有人领养。

生产流程：服务端预分配编号和令牌→按官方硬件设备接入申请model_id和NFC能力→按审批的一机一码模式生成含设备sn及公开tag参数的专属Scheme→批量写NDEF URI Record与Android AAR→读回比对→配对打印私密激活卡和编号→封装后逐件验收。NDEF容量按实际Scheme长度及AAR开销选型，不能预先保证任意NTAG容量够用。锁定只读前核验内容、设备唤起与售后换签方案，锁定后不能依赖消费者重写。

用户扫码后服务端核验私码并显示待领养编号，明确确认后事务绑定账号；如果产品坚持“扫码后再碰一下才完成”，扫码仅创建短期pendingClaim（不先授权），第二次NFC入口用公开令牌解析同一实例，与当前账号待确认会话比对，再确认完成。不能用容易丢失的页面内变量跨小程序冷启动；会话须在服务端保存并有有效期。iPhone可能需要点击系统通知后返回小程序，不能承诺全机型无需点击自动登记。没碰到、超时、错配均不核销，支持重新扫码或明确降级确认。

领养后别人碰一碰：公开令牌→服务端解析实例→返回No.0001、角色公开状态及是否可公开的资料→pages/card/index显示编号和一句话。既有小程序运行中也需检查入口参数变化，防止连续碰0001和0002仍显示前一只；冷启动与热启动均验收。公开入口不返回手机号、私码、持有人身份，不授予衣橱或领养权限。

## 平台能力与限制

- 官方“NFC标签打开小程序”支持符合条件的Android和iPhone，iPhone需XS及以上、设备解锁，并需点击通知；系统钱包、相机、飞行模式等状态影响唤起。这与小程序内直接读写NFC不是同一能力。
- 官方NFC Scheme需国内非个人主体、硬件设备接入、能力审核、model_id，以及已发布的目标页面；一机一码需sn。服务端调用generateNFCScheme，密钥不放前端。审批结果、额度、生成频率和实际机型验收是批量生产前置条件。
- 小程序内主动读写路径为wx.getNFCAdapter → onDiscovered → startDiscovery → 匹配标签技术 → connect／读写 → close／stopDiscovery。当前官方API页标注iOS、Android、鸿蒙支持，但官方近场通信指南仍明确写支持平台Android；两页口径不同，不能据此承诺iPhone可直接写卡或读取UID。直接读写仅作逐机型验证的辅助路线，主流程不依赖它。
- 不新增未经核实的permission配置、不把普通NFC UID当秘密或防复制凭证。普通NDEF入口可能被复制；私码核销和后台状态负责领养权，若需要芯片级防伪应另选支持密码学认证的标签并单独评审。

## 分级降级 仍能领养

| 条件 | 编号与触碰效果 |
| --- | --- |
| 已完成逐只NFC预写、后台与私码配对 | 首选；激活、个人详情、任何人碰一碰均显示同一固定号，无需激活时写芯片 |
| NFC仍为统一款式入口，但私码已逐件配号 | 扫私码即可领养并在个人页显示固定号；公开碰一碰只能显示款式，不得猜测当前碰到哪只。仅需NFC逐件区分，编号可存在后台，无需芯片直接存“No.0001”文字 |
| 既无预分配号也未逐件写标签 | 服务器在首次成功核销私码的事务中分配唯一序号；重复请求返回原号，不用时间戳直接充当序号。它是激活顺序号，不能宣称已对应某个物理芯片 |
| 无NFC或机型不兼容 | 私密卡扫码／手输领养；公开卡片可另给同一公开令牌的二维码作访问入口，严禁复用私密激活码 |

几千至几万只的关键是批量写卡与配卡质检，不是让每位消费者现场写卡。按批次记录写入、回读、打印、配对、封装状态及失败重试，支持编号10000以上、停用／换签保留历史；服务端数据库唯一索引、核销事务、账号鉴权、幂等键和审计缺一不可。

## 后端契约与验收

建议接口（尚未实现）：POST /public/tags/resolve 用公开令牌查询实例；POST /claims/preview 用私密凭证返回待确认编号并创建短期会话；POST /claims/confirm 用账号、会话、可选触碰凭证和幂等键事务核销；GET /me/instances 返回真实归属。序号和owner只能由服务端决定，前端tag、role、serial参数不是鉴权依据。

验收至少包括：同款两只号不同；001卡不能激活002标签；无效tag不回退为0001；取消确认不领养；同账号重试幂等、跨账号核销冲突；公开转发不含私码且不授予权益；批量10000以上不截号；扫码→碰触跨冷启动和热启动；iOS／Android／鸿蒙及无NFC失败兜底；失效私码、网络中断和售后换签。后端与NFC实物验证完成前不得宣称本Demo已支持真实登记。
