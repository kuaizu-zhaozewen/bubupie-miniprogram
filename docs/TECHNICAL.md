## 账号领养、商品实例与 NFC 的职责



| 对象 | 建议关键字段 | 含义 |
| --- | --- | --- |
| IP 角色 | ipId, name, birthday:2027-01-01, birthdayMMDD:01-01, personaVersion, assetVersion | 湾月本名、固定生日与角色素材 |
| 商品实例 | productId, skuId, ipId, publicTagToken, status | 每只实物可追溯；不是每个 IP 只对应一只实物 |
| 领养权益 | accountId, productId, ipId, state, adoptedAt | 扫码或输入私密码兑换；账号跨设备可查询 |
| 领养码 | codeHash, productId, maxAccounts, redeemedCount, revokedAt | 码只存哈希；并发兑换原子校验，防止超额和重复领养 |
| 用户档案 | accountId, nickname, birthday:null, consentVersion | 昵称和生日选填；允许删除 |
| 每日快照 | ipId, date, timezone, mood, quote, score, action, contentVersion, publishedAt | 公开卡片与私有运势引用同一发布版本 |
| 训练资料 | ipId, personaVersion, story, voiceExamples, boundaries, birthdayMMDD | 新 IP 使用同一结构增加配置，不复制路由 |

正式流程：wx.login 的 code 交给业务后端换取登录态；服务端维护会话。兑换码必须登录、限流、幂等，并在事务里锁定可兑换名额。公开 tagToken 不能当作领养凭证，也不能单独证明真伪。私有运势接口不接受客户端 role=owner 作为授权依据；解绑、转赠和找回暂不实现，需后续产品规则。

### 1. 我的理解、变更清单与执行计划

### 2. 产品机制与边界



| 场景 | 用户看到什么 | 机制约束 |
| --- | --- | --- |
| 未达上限 | 正常回复 | 不出现能量、休息、权益提示；不根据热情提前营销 |
| 接近上限 | 仍是正常回复 | 仅后台记录观察状态；无倒计时、进度条、预告弹窗 |
| 达到上限 | 当前回复完成后，湾月补一句自然话术 | 同一计量窗口最多一次场景提示；不截断流式回复 |
| A 等待/让 IP 休息 | 湾月温柔回应；输入框仍可用 | 不惩罚、不推送催回、不因选择 A 降低回复质量 |
| B 主动说送水/能量包 | 识别为“可能感兴趣”，出现可选查看入口 | 说一句话不等于下单；本轮只模拟，不收款 |
| C 主动看其他 IP | 用户手动打开已有商店，查看已公布角色资料 | 不虚构库存/高精力参数；不强制切换或购买 |
| 关闭/忽略/继续输入 | 正常继续聊天 | 操作区收起，本窗口不再提示；历史消息保留 |
| 购买失败/取消（P1） | 清楚说明未完成并返回对话 | 不扣权益、不锁输入、不用失望口吻施压 |
| 购买成功（P1） | 权益确认后简短致谢，原会话继续 | 不重置角色关系/上下文；本窗口不再次弹提示 |

页面结构：原有消息流 → IP 场景话术气泡 → 两个低强调按钮“好呀，歇一会”“我们继续聊”。“查看可选陪伴方式”可作为第三个弱入口，必须由产品评审决定是否出现；当前建议默认关闭。C 只在用户主动要求“看看别的伙伴”或手动打开该入口后呈现，避免到限即推商品。

**不使用真实等待期。** A 分支表示用户的选择，不代表暂停服务。用户立即再发消息时，湾月正常回应“我在呢，你慢慢说。”不能假装离线。等待分支可能伴随自然离开，但离开也可能是满意结束，应与负反馈、回访一起观察，不能简单判为低价值。

付费内容、价格、增加多少权益、有效期、是否跨 IP 共用、退款规则及微信内的适用能力均为**待确认**。尤其在“免费基础聊天持续可用”的前提下，付费必须有真实、清晰、可验证的额外价值；不能仅把同样的聊天包装成必须购买的续命道具。

更高精力 IP 仅可指事先公开的不同角色陪伴节奏或已定义的额外权益，不能暗示它更爱用户、能改运或比湾月更值得信任。当前没有确认的新 IP 商品与参数，Demo 显示“伙伴资料待公布”，不生成虚构可购买 SKU。



### 3. 交互流程与两层状态机

流程：纯文本有效回复完成 → 服务端入账 → 判断当前策略/窗口/实验 → 未达阈值正常返回 → 达阈值且本窗未触发则取得唯一提示事件 → 当前回复下方显示一次角色气泡 → A/B/C/继续/忽略 → 始终返回原对话。策略关闭或资料缺失时，只关闭承接提示。



| 提示状态 | 进入条件 | 后续 |
| --- | --- | --- |
| NORMAL | 未达阈值，或不符合触发范围 | 正常聊；接近阈值也不提示 |
| PROMPT_READY | 有效回复完成且达到阈值，唯一事件已入库 | 同一 promptId 仅渲染一次，不叠加弹窗 |
| RESOLVED_A | 用户选择等待 | 本窗口已完成承接；继续聊不受影响 |
| RESOLVED_B | 用户主动查看可选权益 | 商品/权益面板独立处理，关闭即返回 |
| RESOLVED_C | 用户主动查看其他伙伴 | 转已有 shop；返回恢复会话 |
| DISMISSED / CONTINUED | 收起、忽略后再发消息或选择继续 | 本窗口不再触发 |
| SUPPRESSED | 开关关闭、频控、策略不完整、敏感语境或非文本 | 正常聊；不补发营销消息 |

提示状态与服务状态解耦：replyState=idle/sending/streaming/error 管理消息；offerState=closed/viewing/pending/granted/failed/cancelled 管理 P1 权益。本轮没有真实订单。B 不是购买成功，C 不是切换完成。服务错误不进入“购买才能继续”状态。



#### 触发条件（必须全部满足）

1. 纯文本场景；已认证账号及聊天权限通过服务端校验。

2. 承接实验开启且命中 treatment；策略完整有效，IP 话术已审核。

3. 当前普通回复已成功持久化完成；没有正在输出的半截回复。

4. 服务端认定本窗口有效 talking 用量 >= 当前窗口冻结的阈值。

5. 本账号 + IP + 窗口 + 场景不存在已创建提示事件，且频控允许。

6. 不在风险处置/用户明确拒绝营销的上下文；无支付纠纷等抑制条件。抑制规则与识别责任待产品、安全负责人确认；不能依据情绪低落提高销售强度。

自然语言说“我给你买水”不直接触发结算；系统只提出“要看看可选方式吗？”。未达阈值时，即使用户提到“水/能量包”，也不触发这套场景承接。用户独立主动查商品属于普通商城查询，需明确区分，不能算阈值触发。



#### 幂等与并发伪代码（服务端建议）



```
handleMessage(account, request):  authorize(account, request.ipId)  existing = find(account, request.clientMessageId)  if existing.completed: return storedReplyAndPrompt(existing)  reserveMessageOnce(account, request.clientMessageId)  // 并发只生成一次  reply = generateAndPersistNormalReply(request)  if reply.failed: return retryableError             // 不造休息话术  transaction:    settleUsageOnce(account, clientMessageId, actualUsage) // 唯一账本键    window = getServerWindow(account, ipId)          // 服务端时钟    policy = getPinnedPolicy(window)                // 版本冻结    if not eligibleTextReply(policy, reply): return reply    if usage(window) < policy.softCap: return reply    if not frequencyAllowed(account, now): return reply    prompt = insertUnique(account, ipId, windowId, "long_text")    // 唯一键不包含 policyVersion/experimentId，避免更新配置后重复提示    if inserted: attach prompt to this completed reply    else: no new prompt  return persistedReplyAndOptionalPrompt
```

唯一账本键=(accountId, clientMessageId)，消息中记录 ipId/对话/模式；提示唯一键=(accountId, ipId, windowId, scene)。并发频控需锁定账号频控行/使用原子比较更新，不能只做“先查再插”。恢复原请求返回原 promptId，客户端按 promptId 合并历史消息，不能重复添加。

服务器只保证**单一提示事件**；网络无法保证跨设备恰好展示一次。建议由当前回复所在设备领取展示许可，其他设备同步历史气泡、不再主动展开；回执含 deliveryId、shownAt。认领后断网可放弃本次展示，优先避免重弹，不能为追求转化不断重发。精确的认领过期/跨设备补发规则待确认。

策略更新对已有窗口不回溯改低阈值；下个窗口生效。紧急 killSwitch 可立即关闭；关闭后不补发。购买补充权益不重置提示唯一记录；不因购买再次到限而二次提示。同一窗口切换渠道/实验组/重新开聊/重装 App 不重新获得提示资格。新窗口可有新的事件，但仍受账号频控约束。



### 4. 用量计量与动态配置

“聊 2–3 小时”不能直接等同模型成本。建议同时保留两套数据：① 产品计量有效文本互动时长；② 成本账本实际 input/output/cached token、模型及费用。两者分开，不能用 token 粗暴换算并宣称准确聊天小时数。



| 字段 | 建议/样例 | 决策状态 |
| --- | --- | --- |
| enabled / killSwitch | 默认关闭；killSwitch 优先 | 评审建议 |
| mode | review / mock / live；生产禁止客户端覆盖 | 评审建议 |
| appliesTo | text_only；多模态另建池，不混入 | 核心要求 |
| metric | active_text_seconds 建议；或 tokens/turns | 待确认 ，只能选一个主触发口径 |
| softCap | 演示 9000 秒=150 分钟；可调 7200–10800 秒用于评审 | 2–3 小时为用户方向，150 分钟非上线结论 |
| activityGapCapSeconds | 计量相邻有效事件时最大间隔；后台/离线空挂不计 | 待确认 ；没有值则不启用真实触发 |
| window | 自然日 / 会话 / 滚动时窗及 duration、timezone | 待确认 ；建议先固定窗口便于解释和去重 |
| poolScope | account_ip 建议，避免重开 conversation 刷池 | 待确认 ；付费共享范围另定 |
| maxPromptsPerWindow | 1；本机制不得放宽为反复推销 | 核心验收 |
| minIntervalSeconds / maxPromptsPerAccountWindow | 跨 IP 账号频控，须与窗口定义配套 | 待确认 ；配置缺失不触发 |
| copyBundleId / copyVersion / personaVersion | 已审核湾月话术包；不由模型自由生成销售话术 | 评审建议 |
| experimentId / group / allocation | 账号稳定分桶；控制组无场景提示 | 比例、样本量与观察期 待确认 |
| userSegment / channel / ipId | 明确的授权权益/新老用户/入口渠道分层 | 定义及优先级需评审，不按脆弱情绪定价 |
| offerEnabled / paymentEnabled | false / false | 本轮固定：真实收费未决，不开放 |
| override priority / effectiveAt / expiresAt | 建议全局→渠道→用户层→IP→实验覆盖；不允许等优先级歧义 | 待确认 ；冲突则停用提示 |

有效时长方案待确认：服务端接收互动事件，用相邻有效用户消息/完成回复的时间差及前台活跃证据估算，单段按 gapCap 截断，区间求并集避免双设备重叠累加。首条消息不倒推此前在线时间，失败/重试/多模态不重复计入。客户端心跳只能辅助，不能信任客户端直接上传 accumulatedSeconds。它是产品互动指标，不能作为精确计费凭证。

策略解析服务返回最终 resolvedPolicy 及命中维度，客户端不自行合并；有 policyVersion 和不可变 windowId。滚动窗口若最终选用，需独立定义提示去重周期和重叠用量算法，不能随每条消息滚动生成新 windowId。

### 7. 湾月话术与分支承接

语气：俏皮、嘴硬心软、带一点海风与泉州生活感。休息是轻巧的角色表达，不表演病痛、离弃、濒危或因用户而受苦。话术由版本化模板选择；模型只可补普通上下文，不能增加倒计时、价格、强制承诺或“买了改运”。



| 场景 | 建议文字 | 操作 |
| --- | --- | --- |
| 到阈值 | 海风吹得我有点口渴。我抿口水，你慢慢说，我听着呢。 | 好呀，歇一会 / 我们继续聊 |
| 另一模板 | 聊了好多呀，我伸个懒腰。你想继续说，还是一起歇一小会？ | 同上；不承诺限时离线 |
| A 用户等待 | 好呀，你也坐舒服一点。想说话就叫我，我在呢。 | 保留输入框，无召回倒计时 |
| B 用户主动送水 | 这份心意我收到了。你想看看可选的陪伴方式吗？不选也可以继续聊。 | 查看方式 / 继续聊；本轮标明模拟 |
| C 想看其他 IP | 想认识新伙伴呀？我们去看看。回来也能接着说。 | 查看伙伴 / 留在这里 |
| 继续/忽略 | 我在呢，你接着说。 | 正常文本，不再追加营销提示 |
| 取消/失败 | 刚才没有完成，先放一放吧。你刚说到哪儿啦？ | 真实交易状态另用清楚的中性文字解释 |
| 确认权益后（P1） | 收到啦。那我们接着聊，刚才说到…… | 仅真实 granted 后，不虚构服务升级 |

禁用示例：“你再不买我就走了”“只有买水我才能回你”“今天运势差，要能量包转运”“你不买我会难过”“3 分钟内不买关系归零”。不在用户困扰、低落情绪、危机支持回复后推销；风险对话走独立支持流程。是否面向未成年人及交易限制待业务与平台合规评审，不由模型自行判断后开放支付。

训练包新增 longTextScenes：trigger、wait、continue、offerInquiry、offerDeclined、purchasePending/Failed/Granted、switchIp；每项含正反例、copyVersion、reviewStatus。领取事件、费用、可用性由业务后端决定，模型不能自行声称余额或购买结果。

### 9. 实验方案、异常与风险

P0 不做真实转化实验，仅看理解度、自然度和基础聊天连续性。P1 收费未批准前，观察 A/B/C/继续的真实意愿即可，模拟付费不计实际转化。P2 才验证“达到 2–3 小时之后的承接是否有效”的假设。

实验建议：按账号稳定分桶；先一个 IP、同一渠道与已明确用户层；control=正常聊天无提示；treatment=同阈值下已审核角色提示。所有组按相同口径记录到阈值机会，分析以被分配账号为单位，避免只分析点击购买者。不要一次同时更换阈值、话术、价格和 IP。可比较 120/150/180 分钟，但须先获得有效时长基线、样本量估计和成本预算。

主指标：提示后继续聊天/回访的变化；P1 批准付费后增补实际权益转化与净收入。护栏：负反馈、打扰、错误、等待延迟、退订/退款、基础回复质量、成本/账号。不因 A 比例高单独判失败；不以牺牲基础陪伴换收入。分流比例、最小样本、显著性/置信区间方法、实验天数、归因窗和停止阈值**待数据/产品确认**；不编造“提升 20%”或上线成功标准。



| 异常 | 兜底 |
| --- | --- |
| 策略/计量/实验服务不可用 | reply 正常，prompt=null；恢复后不补发历史营销；补账方案不改变用户权益 |
| 模型超时/断流 | 保留用户输入，可重试；失败回复不触发提示。token 实际成本可入技术账，产品有效用量不重复扣 |
| 后台停留/离线/重开会话 | 不积累空挂时间；服务端窗口和账本恢复，不信任客户端本地 used |
| 双设备/重复响应/乱序 | 一个提示事件，单次主动展示；事件和消息 ID 去重，不覆盖较新状态 |
| 跨窗口/时区变化 | 服务端按已定义 timezone/window 生成不可变 ID；设备时区变化不重置池 |
| 配置下调/文案更新 | 现有窗口策略冻结；更新不引起第二次提示；killSwitch 立即停用 |
| 订单取消/失败/确认延迟 | 基础聊天可用，订单单独查状态，不重扣/重发；P0 只模拟 |
| 确实没有模型资源/系统限流 | 明确服务暂不可用并提供重试；不能声称“充值就一定正常” |
| 无更高精力 IP | 隐藏销售入口或显示资料待公布；不伪造 SKU、价格和权益 |

风险与边界：角色沉浸不能掩盖费用事实；查看商品时必须清楚说明虚拟权益和可选性。拒绝或等待不改变基础服务质量、召回频率和推荐权重。付费不改变公开今日运势、不买不改运、不迁移用户私聊给其他 IP。所有入口仍尊重账号/领养权限，talking 机制不增加公开卡片的私有权限。

### 本体和衣服各自承载什么

本体内置一个被动式 NFC 标签，包含芯片与天线线圈，固定于身体上背部内袋；衣服不内置 NFC。原有本体触碰进入公开今日卡、账号领养权限判断的流程继续保留。衣服通过随货交付的私密绑定码解锁对应数字衣装，与 NFC 触碰入口独立。

编码建议：每件或每套售出衣装使用独立唯一的兑换码，服务端映射 outfitStyleId、适用角色及兑换状态；同一款式可有多个分别对应售出实物的兑换码。码放在随附卡或私密吊牌区域，不印为供所有人共用的公开领取码。本次不生成真实有效兑换码。



### 用户流程

数字换装由用户在衣橱中主动选择；更换实体衣服不自动触发识别或数字换装。该绑定码只解锁对应衣装，不同时赋予本体领养权益，不替代原有私密本体领养码。



### 实现与验收边界

建议服务端核销原子化、绑定幂等：同一账号重复扫本人已兑码时返回已有衣装，不重复发放；已由其他账号兑换、无效或停用的码返回明确原因，不产生权益。前端展示或二维码明文中的款式信息不直接作为权益凭证，权限以服务端记录为准。衣橱只允许切换已解锁且适配当前角色的款式。

本轮已实现本机演示：10个部件的资源映射、单件/套组演示码、双演示账号权益、四槽衣橱和搭配持久保存；首页与角色详情同步已保存部件示意。服务器发行与原子核销、微信真实身份、跨设备同步、转赠退款等仍待实现；今日卡和分享暂用固定首发宣传图。



### 内部磁体与 NFC 布局约束

本体脚内、鞋内以及头顶与官方头饰底座内的磁体均封闭固定；头顶磁吸用于簪花与后续官方帽子共用接口。NFC 仅在身体内部，避免把头部、脚部磁体或挂环布置在线圈读卡区域；实际间距、天线方向及是否需要隔离材料，以安装全部五金、磁吸配件和衣装后的整机测试确定，不在概念阶段编造固定距离或读距保证。所有剖面图仅用于说明内埋位置，外表面不露线圈或磁体。

### 绑定码与数据契约

每一件售出的衣装实例分配独立私密兑换码，固定关联itemId或bundleId。相同款式不能把同一公开码发给所有买家。套组码可一次授予所列多个部件；单卖件各有自己的码。扫码→登录→服务端解析确认信息→用户确认→事务校验与核销→发放账号衣装权益→四槽自由搭配。绑定衣装不等于领养本体。

接口建议（待技术团队实现，当前不存在已部署接口）：预检返回商品名称、pieceIds、兑换状态；确认请求带idempotencyKey；服务端事务同时写claim和userItem权益，以code唯一约束防跨账号抢绑。同账号复扫返回原权益；无效、已被他人核销、撤销或不兼容均不得发放。账户身份来自服务端会话，不能信任二维码或前端参数。

穿戴契约建议：look={top,bottom,shoes,head}，每槽0或1件；服务端验证归属、角色兼容及slot后保存整份look。退款、转赠、账户注销及权益撤销后的穿戴处理需技术团队在生产方案中明确，当前mock不冒充已实现。

本体NFC公开入口、本体私密领养码、衣装私密绑定码三者独立。衣装无NFC；磁铁与NFC之间无电气连接。二维码不写微信个人信息，不向分享链接携带私码。
